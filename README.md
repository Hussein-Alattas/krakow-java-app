# Steps:

### Step 1: GitHub repository 

1. GitHub > New repository > krakow-java-app > Public > Create. 
2. Upload the contents of the project folder (not the folder itself) > Commit to main. 
3. Check that buildspec.yml and appspec.yml are in the root and the video is at src/main/resources/videos/krakow.mp4.


### Step 2:  GitHub Connection

1. Developer Tools > Settings > Connections > Create connection > GitHub > name github-krakow. 
2. Authorize AWS Connector for GitHub > Install a new app > Only select repositories > krakow-java-app. 
3. Connect. Status: Available.

### Step 3 : IAM Roles

| Role | Trusted entity (how created) | Policies |
|------|------------------------------|----------|
| `krakow-build-role` | AWS service > CodeBuild | `AmazonS3FullAccess`, `CloudWatchLogsFullAccess` |
| `krakow-deploy-role` | AWS service > CodeDeploy > use case CodeDeploy | `AWSCodeDeployRole` |
| `krakow-ec2-role` | AWS service > EC2 > plain EC2 use case | `AmazonS3ReadOnlyAccess`, `AmazonSSMManagedInstanceCore` |
| Pipeline role | Created by the CodePipeline wizard (New service role) | Generated by AWS |

> **Note:** My first plan was to use custom least-privilege policies. The final setup uses AWS managed policies, which is simpler but broader.

### Step 4: Network 

VPC by design, doesn't have access to the internet. It needs an Internet gateway, a route to it, a public IP on the instance, and a security group that allows traffic. Please create the following components accordingly. 

1. Create a VPC
3. Create a Subnet
4. Create a IGW
5. Associate RouteTable
6. Create security group
7. Disable ssh, no key pair needed
8. User Data:

   ### Instance user data

```bash
#!/bin/bash
dnf install -y java-21-amazon-corretto-headless ruby wget

useradd -r -s /sbin/nologin krakow
mkdir -p /opt/krakow-app

cat > /etc/systemd/system/krakow-app.service <<'EOT'
[Unit]
Description=Krakow Java app
After=network.target

[Service]
User=krakow
Environment=PORT=8080
ExecStart=/usr/bin/java -jar /opt/krakow-app/krakow-app.jar
Restart=on-failure

[Install]
WantedBy=multi-user.target
EOT
systemctl daemon-reload

cd /tmp
wget https://aws-codedeploy-eu-central-1.s3.eu-central-1.amazonaws.com/latest/install
chmod +x ./install
./install auto
systemctl enable --now codedeploy-agent
```

### Step 5: CodeDeploy

1. CodeDeploy > Applications > Create application > krakow-java-app > EC2/On-premises. 
2. Create deployment group > krakow-java-dg: 
 - Service role: krakow-deploy-role 
 - Deployment type: In-place 
 - Amazon EC2 instances: key Name, value krakow-java-server 
 - Install AWS CodeDeploy Agent: Never (user data installs it) 
 - Deployment configuration: CodeDeployDefault.AllAtOnce 
 - Load balancing: off 
 - Rollbacks: Roll back when a deployment fails 
3. Check: 1 matched instance.

# CI/CD tests: 

### Test 1: a change deploys by itself (CD)

1. In GitHub, open `App.java` and change `VERSION = "1.0.0"` to `"1.1.0"`.
2. Commit to `main`.
3. The pipeline starts by itself, and the Source, Build and Deploy stages turn green.
4. Open `http://<Public-IP>:8080/api/info`. It shows `"version":"1.1.0"`.

**Result: Passed.** The change reached the server without touching AWS or the server.

### Test 2: a failing test blocks the release (CI gate)

1. In `App.java`, on the `/health` line, change `UP` to `DOWN` and commit.
2. The Build stage turns red because the `healthReturnsUp` test fails, and the Deploy stage does not run.
3. The site keeps running: `/health` still returns `UP` and `/api/info` still shows `1.1.0`.
4. Change `DOWN` back to `UP` and commit. The pipeline turns green again.

**Result: Passed.** Broken code was stopped at Build and the last good version stayed live.

# Errors & fixes: 

**Note:** These are the errors I hit while building this project. I'm documenting them so I don't repeat them, and for general awareness.

### Error message: CodeDeploy agent was not able to receive the lifecycle event. Check the CodeDeploy agent logs on your host and make sure the agent is running and can connect to the CodeDeploy server.

#### Deploy stage stuck, then failed

| | |
|---|---|
| **Symptom** | Source and Build were green. Deploy stayed in progress for a long time, then failed. |
| **Root cause** | The CodeDeploy agent was never installed (E2), so nothing on the server picked up the job. |
| **Fix** | Install and start the agent, stop the stuck deployment, then **Retry** the Deploy stage. |
| **Lesson** | A slow Deploy stage usually means CodeDeploy is waiting for the agent. |


 
### Error message: Session Manager couldn't connect; SSM agent could not get credentials

#### Session Manager unavailable

| | |
|---|---|
| **Symptom** | Session Manager was unavailable. Log: SSM agent unable to acquire credentials / error calling `UpdateInstanceInformation`. |
| **Checked (all correct)** | Role permissions, trust policy, role attached, metadata enabled, status checks passed. |
| **Root cause** | The route table with `0.0.0.0/0` → `igw-...` was not associated with the subnet, so the server had no outbound internet and could not reach Systems Manager. |
| **Fix** | VPC > Route tables > Subnet associations > Edit subnet associations > tick the subnet > Save. Reboot the instance. |
| **Lesson** | Check the route table associated with the subnet, not only that a route exists. |
